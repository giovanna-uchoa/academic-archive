This [tutorial](https://flusp.ime.usp.br/kernel/qemu-libvirt-setup/) is part of a four-part series that introduces Linux Kernel development through the Industrial I/O (IIO) subsystem. I followed it to set up a safe and efficient environment for experimenting with custom kernels.

The main goal is to compile and test kernels from source without breaking or polluting the host system. In kernel development, even small mistakes can crash the system, so isolation is essential.

A good environment should be:

* **Safe**: isolated from the host system
* **Efficient**: quick to set up, reset, and iterate on

## Why Virtualization?

When working on the Linux kernel, using your host OS is risky — a bad change can force reboots or even break your system.

Containers are not a solution here because they **share the host kernel**, meaning they don’t provide real isolation.

Instead, this setup uses:

* `QEMU` → full machine emulation (CPU, memory, devices)
* `libvirt` → VM management and networking

This combination allows testing kernel changes safely, with full control over the environment.

## Machine Setup (Disk + RootFS)

The first step was preparing a disk image and expanding the root filesystem.

To inspect the base image:

```bash
du -h <image> # command to check [d]isk [u]sage of files/directories

qemu-img info <image>" #  shows infos about the disk image

virt-filesystems --long --human-readable --all \
  --add <image>  # shows info about partitions and filesystems 
```

This helps identify the correct partition. The root filesystem is typically the one with `ext4`, for example:

* `/dev/sda1` → rootfs (ext4)
* `/dev/sdaX` → EFI partition (vfat)

Then, create a new image and expand the root filesystem:

```bash
qemu-img create -f qcow2 -o preallocation=metadata \
  <image> <memory capacity>

virt-resize --expand /dev/sda1 \
  <source image> \
  <copy expanding the rootfs>
```

Note: After resizing, is important to run `virt-filesystems` again to double-check, because partition labels may change.

## Booting the VM with QEMU

The goal is to test custom kernels, so instead of relying on the image defaults, we boot using:

* a kernel image (`-kernel`)
* an initrd (`-initrd`)

These are usually located in `/boot` inside the rootfs.

Example launch script:

```bash
qemu-system-aarch64 \
  -machine virt \
  -cpu cortex-a57 \
  -m 2048 \
  -smp 2 \
  -kernel <KERNEL_IMAGE> \
  -initrd <INITRD_IMAGE> \
  -append "root=/dev/vda1 console=ttyAMA0" \
  -drive file="${VM_DIR}/arm64_img.qcow2",format=qcow2 \
  -nographic
```

Important details:

* `root=/dev/vda1` must match your rootfs (`sda1 → vda1`)
* You can tweak memory (`-m`) and CPU (`-smp`)
* Even if using the same kernel initially, this setup allows replacing it later

## Managing VMs with libvirt

To simplify VM management, use `libvirt` as the manager and `virsh` as the tool.

Start the libvirt daemon:

```bash
sudo systemctl start libvirtd
systemctl status libvirtd
```

Start the default network:

```bash
sudo virsh net-start default
sudo virsh net-autostart default
sudo virsh net-list 
```

### Useful Commands

```bash
sudo virsh list —all # list all created VMs
sudo virsh dominfo <vm name> # show detailed information about a VM
sudo virsh start —console <vm> # start a terminal window to the previous created VM
sudo virsh shutdown <vm> # gracefully shutdown
sudo virsh destroy <vm> # force shutdown
sudo virsh undefine <vm> # remove a stopped VM
sudo virsh net-dhcp-leases default # get the VM’s IP address
```

## Challenges I Faced

* The `libvirt-qemu` user/group didn’t exist on my system (Fedora dual-boot), so I had to adapt and use `qemu` instead
* The Debian image link was corrupted
* I initially downloaded an amd64 image instead of ARM64, which forced me to redo part of the setup
