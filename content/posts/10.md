For the first phase of the course – the Linux kernel cycle –  I chose to work on a deduplication task previously identified and proposed.

The target was a case of 100% duplicated logic across three files in the AMDGPU tree (`drivers/gpu/drm/amd/amdgpu`). The duplicated code existed in version-specific SDMA implementations and handled the same trap IRQ behavior.

In summary, my proposed change was:
```text
drm/amd/amdgpu: consolidate SDMA trap IRQ handler

Move the amdgpu_sdma_process_trap_irq handler from version-specific
implementations (cik_sdma, sdma_v2_4, sdma_v3_0) to the common SDMA
module (amdgpu_sdma). This eliminates code duplication and centralizes
the trap interrupt handling logic, which is identical across all SDMA
versions.

Update the trap_irq_funcs in each version-specific module to reference
the common handler implementation.
```
The patch significantly reduced repeated code:
```text
 drivers/gpu/drm/amd/amdgpu/amdgpu_sdma.c | 41 ++++++++++++++++++++++
 drivers/gpu/drm/amd/amdgpu/amdgpu_sdma.h |  3 ++
 drivers/gpu/drm/amd/amdgpu/cik_sdma.c    | 43 +-----------------------
 drivers/gpu/drm/amd/amdgpu/sdma_v2_4.c   | 42 +----------------------
 drivers/gpu/drm/amd/amdgpu/sdma_v3_0.c   | 42 +----------------------
 5 files changed, 47 insertions(+), 124 deletions(-)
```
### Challenges and Workflow

The most difficult part was validating the build locally. In this stage, the available CI infrastructure was extremely valuable, making testing much easier and giving confidence before submission.

Another very useful tool was:
```bash
git format-patch -1 --stdout | ./scripts/checkpatch.pl --
```
This helped verify style and patch quality before sending it upstream.

After the CI completed successfully, I sent the patch to the maintainers.

### Review Outcome

Initially, the patch was accepted and applied by Alex. Later, however, another maintainer, Christian, revisited the change and argued that it did not align with the long-term architectural strategy of the project.

The concern was not the correctness of the refactor itself, but maintainability policy: keeping code separated by hardware generation helps prevent future changes in one generation from unintentionally affecting others.

As a result, the patch was dropped.

### Lessons Learned

Even though the patch was not merged permanently, the experience was extremely valuable. I went through the full upstream contribution cycle.

A key lesson was that removing duplication is not always the highest priority. In mature systems like the Linux kernel, maintainers often balance deduplication against stability, isolation between subsystems, and long-term evolution of the codebase.
