This [tutorial](https://flusp.ime.usp.br/kernel/build-linux-for-arm-kw/) is the second part of the newcomers series. After setting up the VM environment with `QEMU` and `libvirt`, the focus now is on actually configuring, building, and booting a custom Linux kernel and testing it.

## Takeaways

* What “building the kernel” means

  Building the kernel is compiling Linux source code into a bootable binary. Not everything is included directly in this image — parts of the system can be built as modules, which can be dynamically loaded and unloaded at runtime.

* Cross-compilation is required in this setup
 
   Since different architectures have different instruction sets, binaries compiled for one will not run on another. In this case, my host machine is amd64 while the target is ARM64, which requires using a cross-compiler (aarch64-linux-gnu-) to generate compatible artifacts.

* Kernel development happens across multiple “trees”
  
    The Linux kernel is not a single repository. There are multiple trees (mainline, stable, subsystem-specific), each maintained by different communities. These repositories are large, so using shallow clones (--depth) and selecting a branch (--branch) helps reduce setup time and disk usage

* `kw` acts as a workflow layer

    `kworkflow` (`kw`) is a FLOSS developer automation tool. It doesn’t replace the kernel build system, but simplifies it by:

    * managing configurations
    * automating build and deploy steps
    * handling remote VM interaction

    It also allows isolated configurations per kernel tree and supports multiple environments, with local settings overriding global ones.

* `.config` is central to the build process

  The `.config` file defines what gets built into the kernel and what becomes a module. It is generated from Kconfig files and used by the build system to decide what to include.

* kbuild is the underlying build system

  The kernel build process is driven by `make` (kbuild). The flow is roughly:
  **Kconfig → .config → Makefiles → compiled kernel + modules**

* There are different ways to generate configurations

    * `defconfig`: baseline configuration
    * `localmodconfig`: minimal config based on currently loaded modules

  Using the VM’s module list to generate a config is a practical way to reduce unnecessary components.

* Avoid editing `.config` manually

   Direct editing is possible but error-prone. It’s safer to use tools like:

    ```bash
    kw build --menu
    ```

## Challenges I Faced

Forgot to pass the VM alias when configuring the remote:

```
kw remote --add vm root@<IP> --set-default
```

Without the alias, `kw ssh` didn’t work properly.

## Commands Cheatsheet
```
### CONFIGURING `kw`
kw init # initialize local configurations for the IIO tree
kw remote --add arm64 root@<VM-IP-address> --set-default # adds a remote named `arm64` to local context and set it to default
kw config build.arch 'arm64' # defines the target architecture to ARM64
kw config build.cross_compile 'aarch64-linux-gnu-' # defines the cross-compiler
kw config build.kernel_img_name 'Image.gz' # defines the kernel image format
kw config --show build # check `kw build` configurations

### CREATING A LEAN `.config` file
make ARCH=arm64 defconfig # create predefined defconfig
make ARCH=arm64 olddefconfig # update defconfig with new default values
kw ssh --get '~/vm_mod_list' # copy VM modules list to IIO tree
make ARCH=arm64 LSMOD=vm_mod_list localmodconfig
kw kernel-config-manager --save arm64-optimized # saves `.config` w/ name `arm64-optimized`
kw kernel-config-manager --list # lists all managed `.config`s
kw kernel-config-manager --get arm64-optimized # gets managed `.config` w/ name `arm64-optimized`

### BUILDING A LINUX KERNEL FROM SOURCE CODE
kw build --menu # safely modify `.config` w/ a TUI
kw build # compile Linux kernel from source considering local configurations

### INSTALLING LINUX KERNEL MODULES
kw deploy --modules # only install modules into the VM

```
